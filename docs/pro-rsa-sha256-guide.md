# تفعيل Mirror Scorpion PRO بتوقيع RSA-SHA256

## النتيجة الحالية

تمت معالجة سبب فشل قراءة المفتاح العام في الاختبار: كانت قيمة السر قادرة على الوصول كـ PEM يحوي محارف `\n` حرفية بدلاً من فواصل أسطر فعلية. أصبح الخادم يطبع هذا التمثيل إلى أسطر حقيقية قبل تمريره إلى `createPublicKey`، ولذلك نجح اختبار الحالة بعد التعديل.

> **حالة التحقق الحالية:** نجحت خمسة اختبارات في `tests/pro-activation.test.ts`، بما فيها اختبار حالة المفتاح العام في بيئة المشروع، واختبار توقيع RSA صحيح بمفاتيح مؤقتة داخل الذاكرة، واختبار رفض ربط الباتش بجهاز آخر أو بباتش منتهي الصلاحية.

## نموذج الثقة

| الطرف | ما يملكه | ما لا يجب أن يملكه |
|---|---|---|
| جهة الإصدار لدى المطور | المفتاح **الخاص** فقط لإصدار التواقيع | لا تضعه في التطبيق أو GitHub أو خادم التحقق العام |
| خادم Mirror Scorpion | المفتاح **العام** في `MIRROR_PRO_ACTIVATION_PUBLIC_KEY` للتحقق | لا يحتاج ولا يتلقى المفتاح الخاص |
| تطبيق الجوال | معرّف تثبيت محلي وباتش PRO الذي يلصقه المستخدم | لا يخزن مفتاح التوقيع أو منطقه السري |

يربط الباتش بين خطة PRO ومعرّف تثبيت التطبيق. لا يعتمد التطبيق على رقم الهاتف أو Android ID أو أي معرف عتادي حساس. يعتمد الخادم على `node:crypto`: يحول PEM إلى `KeyObject` بواسطة `createPublicKey`، ثم يستعمل `verify` لخوارزمية `RSA-SHA256` للتحقق من التوقيع. يدعم Node استيراد مفاتيح RSA بصيغة PEM، ويوصي بإعادة استخدام كائن المفتاح عند الحاجة لتقليل كلفة التحليل [1].

## صيغة الباتش

الصيغة الوحيدة المقبولة هي:

```text
MS4.<base64url-payload>.<base64url-signature>
```

يُحوّل الكائن التالي إلى JSON مضغوط، ثم إلى Base64URL. **السلسلة Base64URL نفسها** هي ما يُوقَّع، ولا يعاد ترتيب مفاتيح JSON أو إعادة ترميزه بعد التوقيع.

```json
{
  "version": 1,
  "deviceId": "MS4-...",
  "issuedAt": 1760000000000,
  "expiresAt": 1790000000000,
  "plan": "pro"
}
```

| الحقل | التحقق الحالي | الغرض |
|---|---|---|
| `version` | يجب أن يساوي `1` | إدارة تغييرات الصيغة مستقبلاً |
| `deviceId` | نص ويجب أن يساوي معرّف التثبيت المرسل | يمنع نقل الباتش إلى تثبيت آخر |
| `issuedAt` | رقم مطلوب | تاريخ الإصدار والتدقيق |
| `expiresAt` | رقم اختياري ويجب ألا يكون في الماضي | دعم الاشتراكات أو التراخيص المؤقتة |
| `plan` | يجب أن يساوي `pro` | يمنع استعمال نوع ترخيص غير مدعوم |

## ما يحدث داخل الخادم

ينفذ `server/pro-activation.ts` التسلسل التالي:

1. يقرأ `MIRROR_PRO_ACTIVATION_PUBLIC_KEY` من بيئة الخادم فقط، ويحوّل `\n` الحرفية إلى أسطر حقيقية عند الحاجة.
2. يحلل PEM عبر `createPublicKey` ويتأكد أن نوع المفتاح `rsa`. إذا فشل التحليل، تكون النتيجة `not_configured` ولا يُفعل PRO.
3. يقسم الباتش إلى ثلاثة أجزاء، ويرفض أي بادئة غير `MS4` أو جزء مفقود أو جزء رابع أو طول يتجاوز 8192 حرفاً.
4. يفك payload من Base64URL ويتحقق من بنيته قبل أي تحقق تشفيري.
5. ينفذ `verify("RSA-SHA256", Buffer.from(payloadPart, "utf8"), publicKey, signature)`؛ وهذا يربط التوقيع بالبايتات نفسها المرسلة في `payloadPart`.
6. بعد نجاح التوقيع فقط، يقارن `deviceId` ويتحقق من `expiresAt`، ثم يعيد `{ valid: true, payload }`.

لا يكشف `pro.status` قيمة المفتاح أو بصمته؛ يعيد فقط `verificationAvailable`، والخوارزمية، وصيغة الباتش. مسار `pro.activate` يستخدم Zod لتقييد طول المعرّف والباتش قبل وصوله إلى دالة التحقق. استخدام `publicProcedure` هنا يسمح بالتفعيل اليدوي من دون حساب مستخدم، لكنه يستلزم إضافة حد للمحاولات قبل الإنتاج التجاري [2].

## ربط المفتاح العام بالخادم

ضع محتوى `public_key.pem` كاملاً في متغير المشروع التالي، مع السطرين `BEGIN PUBLIC KEY` و`END PUBLIC KEY`:

```text
MIRROR_PRO_ACTIVATION_PUBLIC_KEY
```

لا تنشئ ملفاً يحتوي المفتاح الخاص داخل المستودع. لأجل اختبار محلي مؤقت في Termux فقط، يمكن تحميل **المفتاح العام** من ملفه إلى عملية الاختبار:

```bash
export MIRROR_PRO_ACTIVATION_PUBLIC_KEY="$(cat "$HOME/public_key.pem")"
pnpm test -- pro-activation.test.ts
```

بعد تغيير السر في بيئة الاستضافة، أعد تشغيل عملية الخادم أو نفّذ بناءً جديداً حتى تلتقط العملية القيمة. يعالج الكود كلاً من PEM متعدد الأسطر فعلياً وPEM المخزن بمحارف `\n` الحرفية؛ لا يضع المفتاح في متغير `EXPO_PUBLIC_*` ولا في `app.config.ts`.

## كيف يصدر المطور الباتش

يُحتفظ بالمفتاح الخاص في جهاز إصدار موثوق أو خدمة أسرار مخصصة. تُنشأ payload بمفاتيح مرتبة وثابتة كما في المثال، ثم تُشفّر Base64URL، ثم يُوقّع **نص** `payloadPart` بخوارزمية RSA-SHA256. تُشفّر نتيجة التوقيع Base64URL، وتلصق بالأجزاء السابقة مع النقاط.

```ts
const payloadPart = Buffer.from(JSON.stringify(payload)).toString("base64url");
const signaturePart = sign(
  "RSA-SHA256",
  Buffer.from(payloadPart, "utf8"),
  privateKeyPem,
).toString("base64url");
const patch = `MS4.${payloadPart}.${signaturePart}`;
```

> لا ترسل المفتاح الخاص للدعم أو للمستخدم أو إلى جهاز البناء. الباتش الموقّع فقط هو الذي ينتقل إلى المستخدم.

## تفاصيل الاختبارات

| الاختبار | ما يثبته | الاعتماد على سر بيئة المشروع |
|---|---|---|
| `pro.status` | المسار موجود ولا يعرض مادة المفتاح | لا |
| `verificationAvailable` | PEM الحالي قابل للاستيراد ومفتاح RSA | نعم |
| باتش غير صالح | لا يمكن قبول بنية مزورة | لا |
| توقيع صحيح بمفاتيح مؤقتة | صحة التوقيع والتحقق RSA-SHA256 من طرف إلى طرف | لا؛ ينشئ زوج مفاتيح 2048-bit داخل الذاكرة |
| جهاز مختلف | لا يمكن إعادة استعمال الباتش لتثبيت آخر | لا |
| انتهاء الصلاحية | لا يقبل باتشاً صحيح التوقيع بعد انتهاء مدته | لا |

شغّل مجموعة الاختبارات الكاملة قبل أي إصدار:

```bash
pnpm check
pnpm test
pnpm build
pnpm lint
```

## حدود يجب إكمالها قبل الدفع التجاري

التنفيذ الحالي يثبت صحة التوقيع، وربط التثبيت، والصلاحية الزمنية. قبل البيع عبر متجر أو على نطاق واسع، أضف معرفاً فريداً للباتش (`jti`) وسجل إلغاء/حظر خادمي، وحد محاولات لمسار `pro.activate`، وسجلاً تدقيقياً لا يحتوي الباتش كاملاً، واسترجاعاً آمناً لحالة PRO بعد إعادة فتح التطبيق. يجب أن يعاد التحقق من الباتش دورياً على الخادم بدلاً من الوثوق بسجل الواجهة المحلية وحده.
